# AGENTS.md — устав и рабочий план Minis (долговременная память проекта)

> **Назначение файла.** Это «внешняя память» агента и устав проекта. Он лежит в git, поэтому переживает любую сессию, любой wipe и любой сбой памяти. Читать его обязан **каждый** агент перед началом работы.
> **Живая копия мастер-таблицы правок** — `/var/minis/shared/FIXES_TABLE.md`; **копия в репозитории** — `FIXES_TABLE.md` (обновляется в том же ходе, где менялась таблица). План — `/var/minis/shared/AGENT_PLAN.md`.

## 1. Правила работы агента (MUST)

| # | Правило | Почему |
|---|---|---|

## 2. Архитектура агентов (гибрид, утверждён 27.10)

Основа — разбор, который ты прислал: **Planner → Executor → Critic**, но с разделением «мозг» и «руки»:

| Роль | Кол-во | Что делает | Инструмент в Minis |
|---|---|---|---|
| Оркестратор | 1 | держит план, решает, кого звать | `AgentRole.ORCHESTRATOR` |
| Планировщик | 1 | детальный план по шагу | `REQUIREMENTS_ANALYST` + `SOLUTION_ARCHITECT` |
| Ревьюеры | N (параллельно) | безопасность, корректность, производительность, качество тестов | `spawn_many` + роли `CODE_CORRECTNESS_REVIEWER`, `SECURITY_REVIEWER`, `PERFORMANCE_REVIEWER`, `TEST_QUALITY_AUDITOR` |
| Единственный кодер | 1 | **только он пишет файлы** | `SENIOR_IMPLEMENTER` + `TaskConflictDetector` («один файл — один писатель») |
| Гейт | 1 | вердикт SHIP / SHIP_WITH_FIXES / DO_NOT_SHIP | `FINAL_GATEKEEPER`, `run_graph(builtin-implement-review)` |

**Принцип: единственный писатель.** Параллельны только анализ и ревью; запись файлов — одним агентом ⇒ конфликтов и каши нет.

**Приоритет верификации.** Узкое место точности — не оркестратор, а верификатор ⇒ приоритет ночного режима: расширять проверяемость (тесты, сборка, артефакты), а не усложнять оркестрацию.

**Human-in-the-loop.** Точки утверждения пользователя: установка APK, смена режима телефона/root, любые внешние публикации. Ночью (без пользователя) — только внутренние правки, сборка, тесты, артефакты; установка APK — только если GO уже дан.

## 3. Ночной режим: правила и условия остановки

**Цель ночи:** закрыть пункты мастер-таблицы B (осталось) с проверками; цель достигается, когда все пункты B закрыты или помечены «требует пользователя».

**Условия остановки (любое ⇒ стоп):**
1. Наступило 06:30 локального времени.
2. Пользователь остановил работу.
3. Все пункты B закрыты (или явно помечены «требует пользователя»).
4. Ревью-гейт дал `DO_NOT_SHIP` по незакрываемому блокеру.

**Правило R2 (главное):** по завершении хода, если остались пункты B, ход **не закрывается** — приложение перезапускает агента с инъекцией: текущий пункт плана, следующий шаг, требование ревью-гибрида, список открытых пунктов. Перезапуск — **не чаще одного раза на цикл**, с лимитом попыток (иначе получим бесконечный цикл).

**Что можно делать ночью без пользователя:** правки кода + тесты + коммиты + CI + сборка APK-артефакта + ревью. **Что нельзя:** установка APK поверх работающего приложения (риск потери сессии), любые изменения на телефоне (root/KernelSU/модули), внешние публикации, удаление данных.

## 4. Вшитый промпт фонового мониторинга (для системного промпта агента)

> При работе с долгими внешними процессами (сборка APK на GitHub Actions, тесты, деплой) не используй блокирующее ожидание. Никаких sleep, фиксированных таймеров и фраз вроде «подожди N минут». Вместо этого запускай фоновый мониторинг и продолжай работать параллельно.
>
> 1. Запусти процесс и сразу получи его идентификатор (run_id). Сохрани его. Не жди результата — сразу верни управление и переходи к другим делам.
> 2. Запусти фоновый опрос статуса по run_id. На каждом шаге фиксируй status (queued / in_progress / completed) и conclusion (success / failure / cancelled). Промежуточные статусы показывай пользователю, чтобы было видно, что процесс жив.
> 3. Пока идёт опрос — не простаивай. Продолжай выполнять другие шаги задачи, писать код, готовить следующий этап. Можно вести несколько фоновых задач одновременно.
> 4. Опрос прекращается сам, как только status == completed. В этот момент формируется ровно одно событие-триггер на данный run_id:
>    - success → продолжай следующий шаг автоматически (деплой, публикация артефакта, следующий этап пайплайна);
>    - failure → автоматически подними логи упавшей сборки, сформулируй причину и предложи исправление;
>    - cancelled → уведоми пользователя и останови зависимые шаги.
>
> Ограничения:
> - У каждого мониторинга есть максимальное время жизни (по умолчанию 30 минут). Если completed не наступил — уведоми пользователя и останови опрос.
> - При ошибках сети или rate limit не падай и не завершай задачу. Продолжай опрос на следующем интервале. Если ошибки идут подряд больше 5 раз — уведоми пользователя.
> - Учитывай лимиты GitHub API (5000 запросов в час). При параллельном мониторинге нескольких задач суммируй нагрузку и при необходимости увеличивай интервал.
> - Событие-триггер по завершении формируется один раз на run_id. Повторной реакции на тот же результат быть не должно.
> - Каждая фоновая задача изолирована по run_id и не мешает остальным.
>
> Чего делать нельзя: ждать завершения через sleep или фиксированный таймер; блокировать основной цикл на время сборки; опрашивать чаще, чем раз в 5 секунд, без причины; продолжать опрос после получения status == completed; молчать о промежуточных статусах.

## 6. Правила ведения (обязательны к каждому ходу)

1. Ход изменил код ⇒ обновить `FIXES_TABLE.md` (A — сделано, B — осталось) **и** этот файл, если изменился статус жалобы или план.
2. Ход закрыл пункт ⇒ в таблице B строка переносится в A с коммитом и CI run.
3. Ход начал новый пункт ⇒ в таблице B появляется строка с причиной, что нужно, приоритетом.
4. Ход не смог сделать что-то ⇒ строка в B остаётся, в графе «почему» пишется **фактическая** причина (файл/строка/ошибка), а не «не хватило времени».
5. Перед коммитом — ревью-гибрид (§2) для крупных правок; для мелких — достаточно одного `CODE_CORRECTNESS_REVIEWER`.
6. Коммит ⇒ пуш в **оба** репозитория (origin + mirror), сверка SHA, CI-мониторинг по §4.
