# Acceptance-спецификация: цикл отмены/очереди (по внешнему ревью v2)
Статус реализации на момент коммита: liveness-kick — СДЕЛАНО; стресс-прогоны
и idempotent-ack — СПЕЦИФИКАЦИЯ для тест-харденинг спринта.

## Сценарий A: сообщение приходит ПОСЛЕ последнего tail-kick в idle-сессии
Дано: очередь пуста, последний kick уснул (проверил empty → return).
Когда: enqueuePrompt паркует сообщение.
Тогда: [T-queue-liveness] park планирует СВОЙ kick (200мс →
resumeQueueAfterCancel), kick видит непустую очередь → CAS-клейм слота →
drain. Запрещено: зависание до следующего события.

## Сценарий B: процесс умирает непосредственно до/после ack доставки
Дано: durable-first (DB-строка ДО изъятия из очереди).
Смерть ДО записи: очередь цела (memory+persist) → рестор/кик доставляет.
Смерть ПОСЛЕ записи ДО изъятия: DB-строка реальна + persisted-очередь
содержит тот же prompt → СЕЙЧАС at-least-once ДУБЛЬ при ресторе.
Граница (по внешнему ревью v2): пометка ID до принятия = риск ПОТЕРИ;
после принятия = риск ДУБЛЯ при падении между accept и записью ID.
Exactly-once ПРИНЯТИЯ требует атомарной записи приёмника либо
promptId-дедупликации на принимающей стороне. До этого ДУБЛИ —
РЕАЛЬНОЕ поведение (не теоретическое окно); называть доставку
exactly-once ЗАПРЕЩЕНО. Исполнение внешних действий — отдельная гарантия.
Задача харденинга: выбрать схему (атомарный sink vs дедуп по promptId
на acceptor'е) + тесты B-сценария.

→ РЕАЛИЗОВАНО 2026-11-05 (0575f47b): выбраны ОБЕ схемы в одной — атомарный
маркер принятия внутри строки сообщения (messages.source_prompt_ids, JSON

## Сценарий C: гонка под нагрузкой
Stop (force-release слота) → в окне teardown мьютекса N сообщений подряд
(стресс 50+). Успех: каждое сохранено ровно один раз, порядок FIFO
сохранён, ни одного SOF/рекурсии, ни одного зависания; слот/реестр после
серии — свободны (проверка registry via диагностический лог).

## Сценарий D: process death
kill -9 процесса между park и kick; между DB-записью и изъятием; во время
drain. Успех по B выше + восстановление UI без зомби-пузырей
(структурно недостижимо по [T-queue-zombie-window]).

## Критерии успеха (все)
Одно принятое сообщение на один park • правильный порядок • без зависаний •
без рекурсии • registry/slot согласованы после каждого сценария.
