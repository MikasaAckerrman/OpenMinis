## 0. Граница миграции — что заменяем, а что трогать запрещено

Ключевое архитектурное различие, без которого миграция превращается во вредительство:

**Сэндбокс — это продукт.** Alpine-rootfs + PRoot + guest-python — это среда, в которой агент РАБОТАЕТ (инструменты, скрипты, pip). Это не «демон для замены», это фича. В сэндбоксе Rust ничего не заменяет.

**Привилегированные host-сервисы, которые сегодня едут через proot+интерпретатор без продуктовой причины, — вот мишень:**

## 1. Мотивация (все пункты — с уликами, не вкусовщина)

1. **Живой дефект**: vc144-01 (docs/KNOWN_ISSUES_v144.md) — vault-автостарт FAIL; ручной подъём работает, автостарт падает на loader/execve-цепочке proot→python. Расследование 20.10 не дало вердикта (гипотезы SELinux/путь отвергнуты, loader-кандидат не подтверждён). Rust-демон устраняет ВЕСЬ класс: нет proot, нет loader, нет интерпретатора — статический ELF из nativeLibraryDir.
2. **Класс отказа не единичный**: proot-запуск python зависит от PROOT_TMP_DIR (cache→files fallback, PRootKernel.kt:1056-1079), W^X-блокировки self-extracted loader (комментарий PRootKernel.kt:96-108), SELinux-контекста apk_data_file. Каждый из трёх уже давал инциденты.
3. **RAM/CPU**: baseline B30 (AGENT_PLAN.md L173-178) — 193 MB RSS / 156 MB PSS у app; pyrogram-интерпретатор в proot добавляет интерпретатор-heap поверх, недоступный для замеров стандартными meminfo-срезами app-процесса (отдельный pid). Rust-демон: static binary, ожидаемая RSS единицы-десятки МБ (замер в приёмке).
4. **Железное правило №4 (120 FPS)**: тяжёлая обработка — в фоне или в нативном слое. Демон выносит Telegram-I/O из адресного пространства app-процесса вовсе: GC-паузы Compose перестают конкурировать с MTProto-буферизацией.
5. **Supervision-провал зафиксирован**: BASELINE_2026-10-19 «Remaining risks» #3 — vault рестартует только «на следующий старт app». Замена — шанс заложить честный supervisor.

## 2. Целевая архитектура

### 2.1 Один демон `minisd` (не зоопарк бинарников)

```
app-процесс (Kotlin)                     minisd (Rust, отдельный pid)
┌──────────────────────────┐             ┌─────────────────────────────────┐
│ MinisApp.onCreate        │  spawn/fd   │  tokio-рантайм (один бинарник)  │
│  └ DaemonSupervisor ─────┼───(argv0)──►│  ├ vault-модуль (grammers)      │
│     restart w/ backoff,  │             │  │  └ 16 read-only MCP-тулов    │
│     health probe         │             │  ├ jsonrpc-модуль (HTTP 7824 v1)│
│  └ VaultKeystoreCipher ──┼──fd 3───►   │  └ state-модуль (redb)          │
│     (ключ AES-GCM, B4)   │  ключ+сессия│                                 │
└──────────────────────────┘             └─────────────────────────────────┘
```

- **Один бинарник `libminisd.so`** в `jniLibs/arm64-v8a/` (правило API 29+: exec разрешён только из nativeLibraryDir — прецеденты `librg.so`/`libproot.so`, NativeSearch.kt:10-15). Подкоманда выбирается argv: сегодня только `vault`, завтра (трек M) `index`/`mdparse`.
- **Супервизор в app** (`DaemonSupervisor`, новый класс): spawn → probe → restart с экспоненциальным backoff (1s/2s/4s/…cap 60s) — закрывает BASELINE-риск #3. Отдельный daemon-процесс НЕ супервизирует себя (Android убивает детей приложения непредсказуемо; супервизия там, где живёт владелец).
- **Ключ и сессия — через унаследованный fd, не argv/env**: `/proc/<pid>/cmdline` читаем только same-uid, но argv всё равно логируется в ошибок-обвязке; fd 3 = Bearer-ключ + blob сессии. **Шов ревьюера (обязателен к учёту в M-R1):** Android JVM `ProcessBuilder` закрывает нестандартные fd при форке через Zygote (FD_CLOEXEC) — передача через fd 3 требует ЛИБО нативного JNI-хэлпера форка без FD_CLOEXEC, ЛИБО одноразового анонимного Unix-socket handshake в первые 50 мс старта процесса (демон слушает на случайном абстрактном адресе, переданном argv, отдаёт ключ → сокет умирает). Выбор — в реализации `DaemonSupervisor`, зафиксировать в коде с комментарием. Ключ генерируется/расшифровывается существующим `VaultKeystoreCipher` (B4, AndroidKeyStore) — демон НЕ получает доступа к Keystore (он API app-процесса) и не должен.

### 2.2 Контракт IPC — фаза «drop-in»

- **Фаза 1 (M-R2): контракт v1 НЕ МЕНЯЕТСЯ** — HTTP JSON-RPC на `127.0.0.1:7824` + Bearer (`TG_VAULT_AUTH`), `initialize`-probe `isAlive()` (TelegramVaultManager.kt:85-107), 16 read-only тулов, формат ошибок. Kotlin-клиент (`McpCallTool`, чат-путь) не меняется вообще. Риск минимальный, откат — флагом.
- **Фаза 2 (опционально, отдельным вердиктом):** перенос на abstract unix socket `minis-vault` (по образцу NativeOffloadServer, NativeOffload.kt:59-86) — убивает TCP-поверхность с портом (сторонние приложения не смогут даже probing'ом стучаться; сейчас Bearer-гейт B12, но порт виден). Только после стабильной фазы 1.
- **redb для состояния демона** (session-метаданные, retry-стейт): однопроцессный, ACID, zero-copy — по роадмапу Блока 3. КРЕДЕНШЕЛЫ (session auth_key) — файл сессии + шифрование ключом с фазы 1 (fd-injection), redb только для недоверенных метаданных.

### 2.3 MTProto-слой: `grammers`

| Критерий | pyrogram (сегодня) | grammers (миграция) | mtcute/node (отменённый план) |
|---|---|---|---|
| Рантайм | python 3.12 в proot | нативный, статический | node в rootfs |
| Зрелость MTProto | высокая | средняя (active, ton-экосистема) | высокая |
| 16 read-only тулов | готовы | маппинг на raw API — основной труд | почти готовы |
| Сессия | pyrogram SQLite (формат свой) | свой формат → **ре-логин** | свой → ре-логин |
| Класс vc144-01 | подвержен | устранён | воспроизводит |

- Честная цена: **один ручной ре-логин юзера** (поток уже есть — TelegramLoginScreen B4/B17-C; формат сессии несовместим конвертацией, скрывать это нельзя).
- Flood-wait/релеи: grammers отдаёт raw `FloodWait` — оборачивается в retry-политику демона (в pyrogram она была встроенной; недостающее — в нашей обвязке, покрыть контракт-тестами).
- Альтернатива «держать pyrogram, чинить loader-ветку» — отвергнута: исправление автостарта остаётся отдельным проектом со своим baseline (правило vc144-01), но даже успех чинит ОДИН инцидент, а не класс.

## 3. Сборка и CI (правило: локальных сборок нет)

- **Toolchain**: stable Rust, target `aarch64-linux-android` (ndk r28, согласован с deps/build_proot.sh L44-46), `cargo-ndk` в Actions. Ночь x86_64-таргета НЕ делаем (Waydroid-стенд деградирует документированно, как librg). **Ограничение ревьюера:** `-C target-feature=+bti` допустим (SD 8 Gen 3 поддерживает BTI), но НЕ использовать `-C target-cpu=cortex-x4` и прочую микроархитектурную заточку — совместимость со всем кластером (X4 + A720 + A520) обязательна.
- **Workflow**: джоба в Build APK (Unit Tests no-APK не трогаем — cargo там не нужен). Кэш `~/.cargo` + `target/` через actions/cache. Артефакт — готовый `libminisd.so`, линкуется в jniLibs как libproot (deps/build_proot.sh L27-31).
- **Профиль**: `strip + lto="fat" + panic="abort" + opt-level="z"` — ожидаемый размер 1-3 МБ; APK-бюджет сравним с librg (4.7 МБ).
- **ARMv9**: `-C target-feature=+bti` где toolchain поддерживает; strip_pac из B27 (crash_handler.cpp) остаётся в app — демон падает С ТПМБ-СТЕКОМ ОТ ЛОКАЛЬНОГО panic-handler'а в свой лог (не tombstone-зависимый).

## 4. Тест-стратегия (уровни)

1. **cargo test (host)**: маппинг 16 тулов → raw API, retry-политика flood-wait, парсинг JSON-RPC — чистые юнит-тесты в Actions (дешёвая джоба, рантайм ~мин).
2. **Контрактные golden-тесты**: записанные ответы pyrogram v1 (из логов vc144 smoke: tools=20) сравниваются с ответами Rust-демона на тех же запросах — дифф-скрипт в CI, до device-раунда.
3. **Kotlin-интеграция**: существующие тесты Bearer-гейта B12 без изменений = контрак-пин.
4. **Device-приёмка (Блок 2 ADB, iQOO)**: (а) автостарт после рестарта app — порт открыт без ручного подъёма (анти-репро vc144-01); (б) холодный старт до `initialize`-ответа (stopwatch-лог), сравнить с python-бейзлайном **который снять ДО начала M-R2**; (в) RSS демона vs RSS proot+python (ps PID-срез); (г) 24ч фоновая стабильность + батарея; (д) ре-логин-поток на Rust-сессии.

## 6. Риски и честные пробелы

- **[гэп] Бейзлайновых замеров python-vault нет** (разведка: «No daemon-startup-time benchmarks found») — M-R0 обязателен, иначе приёмка неизмерима.
- **[риск] grammers vs pyrogram глубина**: media/ fileSize handling, flood-семантика — карта 16 тулов на raw API готовится в M-R2 и идёт на аудит ДО кода (отдельный дифф-документ).
- **[риск] окно двух демонов**: флаг `vault_impl` + bind-арбитраж (второй на 7824 получает EADDRINUSE → честный лог, не silent).
- **[решено вердиктом ревьюера 07.11]**: pyrogram-путь удаляется ПОЛНОСТЬЮ после закрытия M-R3 (device-приёмка iQOO: 24ч фоновой стабильности, без крашей и утечек). Флаг `vault_impl=rust|python` — только страховочный контур НА период M-R3; после приёмки pyrogram, его скрипты и python-зависимости вычищаются из rootfs и кодовой базы. Мотивация: две параллельные реализации одного протокола удваивают поверхность ошибок, держат мёртвый код и съедают 30-40 МБ rootfs. Никаких вечных фолбэков.
- **[вне скоупа, осознанно]**: guest-python, PersistentShell, PTY, NativeOffloadServer — не мигрируют в Блоке 3.
- **[несовместимость] session-формат**: конвертации pyrogram→grammers нет — ре-логин (см. 2.3).

## 7. Что НЕ меняется (инварианты)

1. Железное правило №7: у агента физически нет тулов удаления аккаунтов — read-only набор Rust-демона наследует список B5 (16 тулов), unlink остаётся только на экране настроек (B17-C).
2. Bearer-гейт B12 (32 байта, HTTP 401) — дословно в Rust-демоне.
3. Контракт 7824 v1 — до отдельного вердикта о фазе 2.
4. TelegramLoginScreen/multi-account UI (B4/B17-C) — Kotlin-сторона не знает о замене сервера.
